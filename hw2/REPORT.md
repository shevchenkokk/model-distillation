# Отчет по ускорению модели **DeepSeek-R1-Distill-Qwen-14B**

## 1. Выбор базовой модели

### Базовая модель
Модель: **DeepSeek-R1-Distill-Qwen-14B**.
- **Тип:** Causal Language Model (контекстное окно, генерация текста).
- **Архитектура:** Decoder-only Transformer (Qwen-based).
- **Параметры:** ~14 млрд (14B).
- **Задача:** Reasoning (логический вывод), решение математических и алгоритмических задач.
- **Сценарий использования:** инференс (интерактивная генерация решений для задач, где важна скорость ответа пользователю, а не обучение).
- **Целевая аппаратная платформа:** 2 x NVIDIA T4

### Узкие места (Bottlenecks)
На основе профилирования базовой версии (FP16) были выявлены следующие проблемы:
1.  **Высокое потребление памяти (VRAM):**
    - Модель занимает **~26 GB** VRAM (в FP16), что требует использования **двух GPU Tesla T4 (2x15GB)**.
    - Это делает невозможным запуск на стандартных видеокартах (RTX 3090/4090 - 24GB, RTX 3060/4060 - 12-16GB, Google Colab Free - 1xT4 15GB).
2.  **Низкая скорость инференса:**
    - Пропускная способность составила всего **2.18 токенов/сек**.
    - Причина: накладные расходы на коммуникацию между двумя GPU (`device_map="auto"` распределил слои, вызвав bottleneck передачи данных). Даже если решить проблему коммуникации между картами, сам по себе большой объем весов создает нагрузку на скорость их чтения из памяти.

### Цель работы
Применить метод ускорения, который позволит:
1.  Уместить модель в память **одного GPU Tesla T4** (< 15 GB).
2.  Достичь скорости генерации не менее **8–10 токенов/сек** (~ в 4 раза быстрее бейзлайна и обеспечивает приемлемый UX).

## 2. Выбор и реализация метода ускорения

Выбранный метод: квантизация из FP16 в 4-bit.

### Почему квантизация?
1.  Снижение веса параметров с 16 бит (FP16) до 4 бит дает теоретическое сжатие в 4 раза.
    - $14B \times 2 \text{ bytes (FP16)} \approx 28 \text{ GB}$
    - $14B \times 0.5 \text{ bytes (4-bit)} + \text{overhead} \approx 7-8 \text{ GB}$.
    Это позволяет модели комфортно разместиться на одной карте T4 (15 GB).
2.  При инференсе модели узким местом является не процесс вычислений, а скорость чтения весов из памяти. Уменьшение размера весов в 4 раза пропорционально снижает объем данных, которые нужно передать из видеопамяти в вычислительные ядра, что ускоряет генерацию. 

### Риски метода
- Потеря точности при округлении весов. Однако для моделей >10B параметров (как наша 14B) 4-битная квантизация (особенно NF4) обычно дает минимальное падение качества.
- В процессе работы веса деквантуются в FP16 для вычислений. Это добавляет вычислительную нагрузку. Но выигрыш от снижения времени на передачу данных обычно снижает эти затраты.

### Алгоритм и реализация метода

Реализация выполнена на Python с использованием библиотек `transformers`, `accelerate` и `bitsandbytes`.

**Ключевые этапы алгоритма (см. `hw2/quantization_experiment.ipynb`):**
1.  **Конфигурация квантизации:** используется объект `BitsAndBytesConfig` из библиотеки `bitsandbytes`. В нем задаются следующие ключевые параметры:
    - `load_in_4bit=True`: режим 4-битной квантизации.
    - `bnb_4bit_quant_type="nf4"`: тип квантизации `nf4` (оптимизирован для нормального распределения весов нейросетей, что позволяет сохранить больше точности по сравнению с обычным INT4).
    - `bnb_4bit_compute_dtype=torch.float16`: тип данных вычислений (для совместимости с тензорными ядрами GPU).
    - `bnb_4bit_use_double_quant=True`: двойная квантизация для сжатия служебных коэффициентов масштабирования.
2.  **Загрузка модели с применением квантизации:** модель загружается через `AutoModelForCausalLM` с передачей конфига. Библиотека автоматически заменяет линейные слои (`Linear`) на `Linear4bit`.
3.  **Запуск генерации:** стандартный pipeline генерации (`model.generate`).

**Почему выбран именно такой алгоритм?**

Выбор данного конфига обусловлен необходимостью решить две основные задачи: максимально снизить потребление памяти и сохранить при этом приемлемую скорость и качество генерации.

## 4. Проведение эксперимента

### Конфигурация среды

- **Аппаратное обеспечение:**
  - **GPU:** 2 x NVIDIA Tesla T4 (по 15 ГБ VRAM каждая, суммарно 30 ГБ).
  - **CPU:** 4 ядра, Intel(R) Xeon(R) CPU @ 2.00GHz.
  - **RAM (ОЗУ):** 31 ГБ системной памяти (System RAM).
- **Программное обеспечение:**
  - **ОС:** Ubuntu 22.04.4 LTS.
  - **Среда:** Python 3.12.12.
  - **Фреймворк:** PyTorch 2.9.0+cu126, CUDA 12.6.
  - **Ключевые библиотеки:** `transformers`, `accelerate`, `bitsandbytes`.

### Данные и параметры запуска

Для оценки метрик использовался фиксированный промпт (задача на логику), заставляющий модель использовать внутренние механизмы рассуждения (reasoning):

> *Промпт: "Реши уравнение: x^2 - 5x + 6 = 0 по шагам"*

Использование единого детерминированного инпута позволяет изолировать влияние длины контекста на скорость и провести чистое A/B тестирование производительности. Если мы будем подавать разные промпты, у них будет разная длина входных токенов и модель будет генерировать разное количество выходных токенов. Сравнивать скорость на разных данных сложнее.

**Гиперпараметры генерации (`model.generate`):**
*   `max_new_tokens=450` — жесткое ограничение максимальной длины ответа,чтобы модель не ушла в бесконечную генерацию.
*   `do_sample=True` — включение вероятностного семплирования (используются дефолтные настройки температуры модели, заложенные в ее `generation_config`).


## 5. Выбор и обоснование метрик

Для оценки эффективности метода были выбраны следующие метрики, напрямую вытекающие из целей работы:

1. **Пиковое потребление VRAM (ГБ):** критическая аппаратная метрика. Показывает, удалось ли нам достичь главной цели — уместить модель в память одного GPU T4 (<15 GB).
2. **Скорость генерации (ток/с):** основная метрика производительности для LLM в режиме потоковой генерации. Определяет UX. 
3. **Общая задержка / Latency (секунды):** время от отправки запроса до получения полного ответа.
4. **Качество генерации (субъективная оценка / логическая связность):** так как модель специализируется на reasoning, важно было убедиться, что квантизация не сломала логику рассуждений (сохраняется цепочка мыслей в тегах `<think>` и итоговый ответ корректен).

## 6. Сравнение модели до и после ускорения

| Метрика | Базовая модель (FP16) | Квантованная модель (4-bit) | Изменение |
| :--- | :---: | :---: | :---: |
| **VRAM (ГБ)** | 26.06 | 9.59 | -63.2% |
| **Скорость (ток/с)** | 2.18 | 6.77 | x3.1 |
| **Задержка (с)** | 206.26 | 41.07 | -80.1% |

### Интерпретация результатов:

1. **Память (VRAM):** потребление памяти снизилось на 63.2% (с 26.06 до 9.59 ГБ). Это успех. Теперь модель свободно помещается в одну видеокарту Tesla T4, оставляя около 5 ГБ запаса под контекстное окно (KV-cache) для длинных диалогов.
2. **Скорость и задержка:** Скорость инференса выросла более чем в 3 раза (с 2.18 до 6.77 ток/с). Общее время ожидания ответа снизилось с невыносимых 3.5 минут (206 сек) до приемлемых 41 секунды.
3. **Качество:** визуальный анализ сгенерированных ответов показал, что модель сохранила способность к логическому выводу.

## 7. Вывод о целесообразности подхода

Применение **4-битного квантования (NF4)** для модели DeepSeek-R1-Distill-Qwen-14B является **инженерно оправданным** и высокоэффективным решением для production-сценариев на ограниченном оборудовании.

### Достигнутые выигрыши и компромиссы
* Инфраструктурные расходы сокращены в 2 раза (нужна 1 видеокарта вместо 2-х).
* Скорость работы модели увеличена в 3.1 раза. Теперь её можно использовать в качестве рабочего прототипа и не пускать слёзы от медленного стриминга.
* *Компромисс*: небольшое отклонение от целевого показателя скорости (6.77 вместо 8+) из-за накладных расходов на деквантизацию и потенциально минимальное (но незаметное на базовых тестах) снижение перплексии.

### Сценарии применения в production:
- **Целесообразно:** в условиях ограниченного бюджета на инференс; при деплое на пользовательское железо (RTX 3090/4090); для создания внутренних AI-ассистентов компаний, где допустима генерация со скоростью чтения человека (~6-7 слов в секунду).
- **Нецелесообразно:** если проект разворачивается на мощном оборудовании (например, кластер из NVIDIA H100/A100). В таком случае памяти хватит и для FP16, а использование фреймворков вроде vLLM или TensorRT-LLM (без INT4 квантизации, либо с FP8 квантизацией) даст пропускную способность в десятки и сотни токенов в секунду без затрат на деквантизацию `bitsandbytes`. Также метод не подойдет, если модель используется для критически точных вычислений, где малейшая ошибка округления весов может привести к галлюцинациям в строгих математических доказательствах.
